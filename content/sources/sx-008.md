## 为什么重要

这篇 2021 年采访把 SpaceX 软件测试基础设施讲得非常具体：谁对 change 负责、merge 前后检查什么、CI 如何吃软硬件遥测、计算资源多大、真实硬件怎样接进自动测试。

它保持 P1，而不是 P0：核心信息来自 SpaceX 工程师 Erin Ishimoticha 的直接采访，但文章由 Stack Overflow 编辑发布，不是 SpaceX 自己发布的原始记录。

## 精确证据地图

### `Check, check, and check again`

文章说明 Software Delivery Engineering 协调 SpaceX 飞行器软件的版本控制、自动测试和人工测试，并维护自建 CI。受访者描述的 CI web service 会摄入软件与硬件测试遥测、画图、运行 assertion，并生成软件表现报告。

同一节明确区分质量等级：从 CI 工具到为乘员提供安全关键功能的 flight software，要求不同；安全关键软件在 merge 前有更多检查和 PR 条件，merge 后还要继续测试，避免 PR 在途变化相互干扰。

### `Watching each other's back`

受访者给出一个具体的软件 Responsible Engineer 流程：

1. 从 backlog 接一个 issue；
2. 理解并复现问题；
3. 设计、实现；
4. 补 test coverage，并在隔离环境做 functional testing；
5. 发 PR，自己找 reviewer；
6. merge 后确认下一次 master CI 通过；
7. 再进入 verification。

同一节称 CI 基于 HTCondor，当时**每月约运行一百万次 CI build**。这个数字只能作为 2021 年规模快照，不能当成当前指标，更不能拿 build 数直接代表质量。

### `Managing builds and rockets on the table`

文章继续给出基础设施细节：

- PostgreSQL 管 build、test result 与 artifact 元数据；
- Docker 用于干净、一次性的 build 环境；
- 当时约有 550 个不同规格的 worker；
- 大量自定义 HITL testbed 直接接进 CI；
- 受访者举例，testbed 会放真实 flight computer、sensor，Dragon 2 座椅台架甚至有真实 actuator。

这些细节能证明“自动化测试”背后确实有大规模计算与真实硬件基础设施，而不只是一个 CI 按钮。

## 能证明什么

- 2021 年 SpaceX Software Delivery Engineering 自建 CI，并把自动测试、人工测试、软硬件遥测和报告连在一起。
- 安全关键 flight software 的 merge 门槛高于普通内部工具；PR review、merge 前检查、merge 后回归是同一链条的一部分。
- 软件 RE 对一个 issue 的责任会跨过复现、设计、实现、测试、review、merge 后 CI，并继续到 verification。
- 当时 CI 规模约一百万 build/月、约 550 workers；大量 HITL testbed 接入 CI。
- HITL 不是纯软件模拟：至少部分 testbed 使用真实 flight computer、sensor 与 actuator。

## 不能据此推出

- 软件 RE 工作流不等同于 SpaceX 所有硬件 RE 的权限、预算或签字范围。
- “类似 NASA 软件分类”不能写成 SpaceX 完整采用某一套 NASA 软件标准；文章只支持“存在不同质量等级”。
- 2021 年的 build 数、worker 数、技术栈不能当成 2026 年现状。
- CI 次数不是质量指标；关键仍是测试覆盖的风险和判定是否有效。
- Stack Overflow 是采访转述，不应把编辑者的概括与工程师直接引语混成同一证据等级。
