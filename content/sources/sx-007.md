## 为什么重要

这是目前最具体的 SpaceX 内部制造软件公开材料之一。文章不是内部架构文档，但包含多位 SpaceX Application Software 管理者的直接引语，能把“数字主线”从抽象概念落到零件、工单、质量、变更和现场制造。

## 精确定位

### 开头：系统到底管什么

文章开头直接列出 Application Software 团队的职责范围：

- 原材料采购与收货；
- 创建和执行 work order；
- manufacturing；
- inventory；
- quality escape；
- change management；
- 发射流程。

Anthony Rose 还给了两个很具体的例子：系统追踪“某个已经制造出来的零件现在在哪里”，以及追踪零件之间的关系，使 defect 或 design change 能沿产品关系看到影响范围。

### “The software stack — from monolith to microservices”

这部分提供了一个重要反例：SpaceX 并不是简单把所有业务永久塞进一个系统。

- 文中把 **Warp Drive** 明确称为长期使用的 monolithic ERP system。
- 2019 年 Starlink 制造需求出现后，团队认为卫星终端制造与火箭制造不同，开始在 Warp Drive 之外建设新的 manufacturing execution system。
- 文章描述新系统与主系统分离，通过异步 API 等方式协作。

这说明可追踪的数字工作流不等于“一个巨型单体工具”。

### “Up, up, and away”

- Application Software 团队面对 Falcon、Dragon、Starlink、Starship 等多条业务线，没有简单按业务数量线性扩张团队，而是调整工作方式。
- 采访明确说，团队把工程师拉近真实问题，尽量缩短“理解问题 → 构建解决方案”的距离。
- 产品决策和工程决策尽量放在同一个人或团队。
- Starlink 软件工程师被搬到装配线旁，并轮班去不同工位实际工作，以理解生产问题。

### “Data data everywhere — or not”

团队强调不要无目的堆数据；应保留真正支持分析和下一次迭代的数据，避免 data swamp。

### 结尾

文章把目标概括为让内部系统连接 digital 与 physical，并把自动化手工工作、提高制造和运营能力作为持续方向。

## 能证明什么

- 2021 年公开采访中，SpaceX 内部应用软件已经直接覆盖供应链、制造、库存、质量、变更和发射流程。
- 零件位置、零件关系，以及 defect / design change 的影响传播，是公开明确描述过的能力。
- Warp Drive 当时是一个长期使用的 monolithic ERP；Starlink 的新制造模式促使团队在 2019 年另建 MES，而不是坚持所有业务共用同一应用。
- 软件工程师贴近装配线、直接体验工位，是这支团队公开描述过的实际做法，不只是管理口号。

## 不能据此推出

- 这是 **2021 年的外部采访**，不是 SpaceX 官方内部架构规范。
- 文章包含直接引语，但仍经过 Stack Overflow 编辑整理；没有直接引语支撑的总结应按采访报道而不是内部制度文件使用。
- 不能据此声称所有 SpaceX 业务线都使用同一套工具、同一个数据库或同一套流程。
- 文中能证明 part relationship / defect / change traceability，但不能单独证明需求、CAD、供应商批次、测试、放行等全部对象已经形成完整端到端 digital thread。
- Angular、Kafka、HBase、Kubernetes 等只是当时时点的技术选择，不应迁移成“SpaceX 方法”。
