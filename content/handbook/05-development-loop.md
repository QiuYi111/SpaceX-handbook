NASA 在 COTS 合作复盘中记录了 SpaceX 快速 Design–Test–Repeat 的工作方式；Muratore 的系统工程材料也明确强调让设计、制造和测试形成短反馈环。{{< source "SX-003" >}}{{< source "SX-002" >}}

它不是“多做 prototype”这么简单。

真正优化的是：

> **一个关键未知，从被提出到被真实证据解决，需要多久。**

## 1. 开发的单位不是任务，而是学习闭环

传统项目管理很容易统计：

- 完成多少图纸；
- 关闭多少 issue；
- 写完多少需求；
- 完成多少分析。

但这些都不等于风险下降。

更有意义的问题是：

> **这一周，我们关闭了哪些关键未知？**

例如：

- 密封结构是否能扛循环载荷？
- 这个连接器在振动后是否还可靠？
- 这个算法在真实传感器噪声下是否稳定？
- 供应商实际能否稳定做出这个公差？

如果没有新证据，任务再多也可能只是“项目很忙”。

## 2. 一个完整闭环

典型硬件反馈环：

**问题 → 假设 → 设计 → 分析 → 制造 → 测试 → 数据 → 解释 → 修改**

任何一段都可能成为真正瓶颈。

所以团队应该测的不是“设计部门效率”，而是整个 loop 的 wall-clock time。

## 3. 真实切片：早期 Merlin 不是“设计完再测试”

Kellan O'Connor 对早期推进团队的回顾，把这个闭环说得比“快速迭代”四个字具体得多：当时 propulsion department 约 **20–30 名工程师**，design engineer 与 analysis、development engineer 紧密合作；设计先做数字分析，再进入实物制造和装配，硬件随后送到 Texas test facility。{{< source "SX-019" >}}

这个案例说明，真正的闭环不是：

> CAD → release → 等别人测试。

而更接近：

> **设计判断 → 分析 → 做出来 → 上台架 → 数据回来 → 原设计者继续改。**

这里最值得学的不是“团队一定要 20–30 人”，而是**负责设计的人离真实后果足够近**。

时间边界也要写清楚：这是 O'Connor 所处时期的早期推进团队切片，不是今天所有 SpaceX 团队的固定规模或标准流程。

## 4. 找最长的等待，而不是最忙的人

假设：

- 设计：1 天；
- review：2 天；
- 采购：12 天；
- 加工：7 天；
- 测试排队：5 天；
- 数据分析：1 天。

总周期 28 天。

即使 AI 把设计从 1 天压到 1 小时，总周期仍然接近 27 天。

因此真正的工程速度优化通常需要动：

- 采购方式；
- 标准件库存；
- 快速加工能力；
- 测试台自动化；
- review 权限；
- 供应商合作方式。

这也是 SpaceX 垂直整合为什么与快速迭代高度相关。

## 5. 实验要回答问题，不要展示进度

差的 prototype：

> “做一个完整样机看看。”

好的 prototype：

> “验证这个密封界面在 10 万次循环后是否仍满足泄漏要求。”

实验越明确：

- 样机可以越简单；
- 数据越容易解释；
- 失败越便宜；
- 下一步越明确。

## 6. 用最低层级解决未知

一个未知可以在不同层级回答：

1. 手算；
2. 仿真；
3. 材料 coupon；
4. 单零件试验；
5. 子系统；
6. 整机；
7. 真实任务。

正确原则不是“尽量实物”，也不是“尽量仿真”。

而是：

> **用最低成本、最低后果，但足够可信的层级回答问题。**

如果 coupon 已经能证明材料不行，没有必要做整机。

如果问题只会出现在整机耦合中，再多 coupon 也替代不了 integrated test。

## 7. 失败必须产生信息

一次 prototype 失败值得不值得，取决于：

- 有没有测到关键变量；
- 能不能定位原因；
- 能不能区分多个假设；
- 数据是否足够进入下一版；
- 下一版能否真正修改。

如果每次都只是“炸了，不知道为什么”，那不是快速学习，只是快速消耗硬件。

## 8. 制造能力决定你能否承担迭代

Kellan O'Connor 对 Merlin 开发的描述反映了一个重要条件：设计、制造和 Texas 测试之间能够快速来回。{{< source "SX-019" >}}

Chris Hansen 后来把类似方法带到核反应堆 startup，也说明这种模式能够迁移到其他高后果硬件，但前提仍是把试验层级和风险边界设计好。{{< source "SX-013" >}}

如果每件原型都需要：

- 半年采购；
- 高额 NRE；
- 唯一工装；
- 长审批；

组织自然会变得极度保守。

因此“低成本快速制造”不是支持部门能力，而是**研发方法本身的基础设施**。

## 9. 强监管行业也能做短反馈环，但证据门槛不能降

Chris Hansen 离开 SpaceX 去 Radiant 后，给了一个很好的迁移反例：核系统并没有因为要快就少做分析和验证。他明确强调 detailed analysis、rigorous testing、validation；同时团队搭建氦循环器 test loop，模拟运行温度和流阻，并把数据回填内部 Digital Twin。{{< source "SX-013" >}}

这个案例不是 SpaceX 流程本身，但它说明一个重要边界：

> **短反馈环的本质是更快得到可信证据，不是降低证据标准。**

对于高后果硬件，真正应该缩短的是：

- fixture / test loop 搭建时间；
- instrumentation 与数据整理时间；
- failure → root cause 时间；
- 修改后重新验证的时间。

而不是把 qualification、verification 或监管要求本身删掉。

## 10. 把学习速度写进项目管理

一个更好的 issue 不只写：

> 完成 PEEK 外壳设计。

而写：

> 验证 0.6 mm 壁厚 PEEK 壳体是否能通过目标机械载荷，并在周五前获得测试结果。

这样 issue 的完成条件不是“CAD merged”，而是“未知被关闭”。

## 11. 反模式

### Big-bang prototype

把几十个未知全部塞进一台整机。失败后很难知道为什么。

### Analysis paralysis

不断增加分析精度，却迟迟不做能显著改变决策的测试。

### Prototype theater

样机很好看，但没有明确验证问题。

### Waiting hidden as work

issue 一直 open，看起来团队很忙，实际 80% 时间在等采购、等 review、等测试。

## 12. 最值得跟踪的几个周期

对于硬件团队，可以长期跟踪：

- idea → first test；
- CAD release → part in hand；
- failure → root cause；
- failure → next tested revision；
- supplier RFQ → usable sample；
- test complete → decision。

这些数字比“本月完成多少图纸”更能暴露真正的组织瓶颈。
