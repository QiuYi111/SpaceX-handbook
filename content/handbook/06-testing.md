“SpaceX 快，所以它少做验证”是一个错误推论。

公开资料显示的方向几乎相反：**越想快速迭代，越需要高带宽测试系统。**

2012 年，SpaceX 系统工程负责人 John Muratore 在公开演讲中直接写到：设计本身要可测试，要 `test what you fly`，并在多个集成层级严格测试；同一材料还给出了当时 Falcon / Dragon 的具体测试层级和链路。{{< source "SX-002" >}}

SpaceX 软件团队后来也公开描述过持续集成、自动测试、硬件在环、人工测试和完整任务模拟；安全关键软件需要更严格的检查。{{< source "SX-006" >}}{{< source "SX-008" >}}

## 1. 测试不是项目尾声

如果产品设计完成后才开始问：

> “这个东西怎么测？”

通常已经太晚。

Muratore 在 2012 年的 **p.7** 直接把 `Design a testable system` 放进 Central Philosophy。{{< source "SX-002" >}}

一个好的工程设计，从早期就在回答：

- 哪些关键状态能观测？
- 故障发生时能不能定位？
- 哪些接口需要 test point？
- 哪些测试可以自动跑？
- 哪些环境必须复现？
- 哪些数据必须记录？

**可测试性本身就是设计属性。**

## 2. Test What You Fly

测试件与飞行件/正式产品之间差异越大，测试结论越弱。

如果测试使用：

- 不同线束；
- 不同软件；
- 不同工装边界；
- 不同材料；
- 不同配置参数；

那么“通过测试”可能并不能证明正式系统。

因此一个重要纪律是：

> **尽量让测试对象、配置和环境接近真实使用状态。**

这不是后人替 SpaceX 总结的口号。Muratore 的 **p.15** 标题就是 `Test Like You Fly, Test What You Fly`，并把 integrated testing tools 称为关键投资。{{< source "SX-002" >}}

## 3. 2012 年的测试链路到底长什么样

“多测”如果没有具体对象，很容易沦为文化口号。2012 年材料给了一张更有价值的工程快照。{{< source "SX-002" >}}

**p.15 的集成节点包括：**

- Hawthorne 的 ironbird：做硬件—软件集成；
- McGregor engine test：发动机与航电在真实动力环境中集成；
- McGregor stage test firing：把贮箱、管路、航电、推进放进同一真实动力环境；
- 发射场 HIL：让硬件和软件与完整系统部件一起跑；
- wet dress 与 pad static fire：在发射场继续做整系统集成。

**p.16 又把测试目的拆开：**

- development test：主动摸能力边界、找弱点，例如扩展温度、极限强度；
- qualification：覆盖最差飞行条件并带安全系数/余量；
- acceptance：检查制造质量与功能，材料写明当时 **all hardware acceptance tested**；
- HITL：验证硬件—软件集成，材料写明随硬件/软件变更运行。

**p.17–18 则把部件、总成、端到端、发动机、结构、航电测试一路连到 integrated stage firing、WDR、pad static firing、post-test / post-flight analysis 和 Flight Readiness Review。**

这里最重要的不是照抄 2012 年 Falcon 流程，而是看见结构：

> **便宜层级高频暴露问题，越接近真实任务，集成范围越大、代价越高、门槛也越严。**

边界也必须写清楚：这是 **2012 年 Falcon / Dragon 语境的一手快照**，不能直接声称 2026 年 Starship、Dragon、Starlink 仍逐项沿用同一流程。{{< source "SX-002" >}}

## 4. 分层测试，而不是只做整机

高质量测试体系通常是一座金字塔：

### 单元 / 零件

便宜、快、适合大量回归。

### 子系统

验证真实接口和局部耦合。

### 硬件在环

让真实硬件与模拟环境闭环。

### 集成系统

发现跨系统耦合问题。

### 真实任务 / 现场

验证只有真实环境才能暴露的问题。

SpaceX 2012 年材料并没有用这五层中文分类，但它确实展示了从 component development / qualification / acceptance，到 HIL、stage firing、WDR、static fire、飞行后分析的多层级测试链。{{< source "SX-002" >}}

因此这里的迁移原则是：快的团队不是跳过下层测试，而是**让每一层尽可能自动、高频、低成本**，减少把简单错误带到昂贵整机测试。

## 5. 自动化测试是研发吞吐基础设施

如果每次改软件都要人工花两天重新验证，团队会自然减少发布。

如果自动测试能在每次 merge 后运行，发布频率就可以显著增加。

SpaceX 软件公开访谈展示了这种思路：自动测试和 CI 承担大量重复验证，而人工测试和完整任务模拟用于覆盖自动化难以替代的场景。{{< source "SX-008" >}}

对硬件同样成立。下面这些是**迁移到一般硬件研发的建议，不是声称 SpaceX 逐项采用同一实现**：

- 自动采集；
- 自动生成 report；
- 自动比较 golden data；
- 自动报警；
- 自动回归。

测试自动化的目标不是“少雇测试工程师”，而是让工程师**敢于更频繁修改系统**。

## 6. 失败后首先保护数据

一个昂贵试验最糟糕的结果不是失败，而是：

> **失败了，却没有足够数据知道为什么。**

因此在试验前就应该检查：

- 关键传感器是否覆盖；
- 采样率是否足够；
- 时钟是否同步；
- 故障前数据是否缓存；
- 视频/遥测是否能保留；
- 触发条件是否可靠。

这一节是从“测试必须产生可用于下一轮设计的信息”推导出的工程规则，不把它伪装成某条 SpaceX 官方制度。Muratore 的材料能直接支持的是：SpaceX 当时明确依赖快速 design-build-test 用经验回灌设计，并设置 post-test / post-flight analysis。{{< source "SX-002" >}}

试验硬件可以损失，信息不能轻易丢。

## 7. 测试强度跟后果一起变化

开发原型和正式载人系统显然不能采用同一门槛。

2012 年 SpaceX 材料给出的分层非常具体：development test 用于找弱点，qualification 覆盖最差飞行环境与余量，acceptance 用于检查每件硬件的制造质量和功能；材料同时指出，系统进入 final qualification、first flight、production 后，文档与流程会更正式。**p.14、p.16**。{{< source "SX-002" >}}

迁移到一般工程，可以用下面的结构理解：

- **早期探索**：快速关闭未知；
- **设计验证**：证明设计满足要求；
- **qualification**：证明设计余量；
- **生产 acceptance**：证明每件产品符合已验证设计；
- **高后果正式任务**：额外独立检查、故障场景和完整系统验证。

前两项和最后一项是本手册为了迁移而做的概括；中间的 qualification / acceptance 则有 SX-002 的直接一手支持。

因此 SpaceX 方法并不是统一“更松”，而是**让开发阶段尽早暴露问题，同时随着产品成熟提高正式度**。这至少可以由 2012 年材料直接确认；不应进一步外推成“SpaceX 对所有项目都降低验证门槛”。{{< source "SX-002" >}}

## 8. 测试不是演示

演示的目标：

> 成功给别人看。

测试的目标：

> 尽可能有效地发现系统哪里错。

Muratore 的 **p.16** 给了一个很好的直接例子：development test 的目的之一就是在超出要求的条件下摸硬件能力、主动找弱点，例如扩展温度和极限强度测试。{{< source "SX-002" >}}

所以真正有价值的测试应该愿意进入边界：

- 高低温；
- 极限载荷；
- 故障注入；
- 断连；
- 异常输入；
- 最差组合。

这里“故障注入、断连、异常输入”等是通用工程扩展，不是 SX-002 对 SpaceX 的逐项清单。重要的是测试目标：找弱点，而不是挑最容易通过的条件。

## 9. 一个简单的测试定义

每个重要测试至少回答：

| 项目 | 问题 |
|---|---|
| Question | 我们到底想知道什么 |
| Configuration | 测的具体版本是什么 |
| Pass criteria | 什么结果算通过 |
| Instrumentation | 需要测哪些量 |
| Failure handling | 失败时如何保证安全和数据 |
| Decision | 结果出来后会改变什么决定 |

这张表是本手册的**迁移工具**，不是 SpaceX 原表。

如果最后一项回答不了：

> “无论结果如何，我们都不会改任何决定。”

那这个测试很可能没有必要。

## 10. 反模式

- 测试写在项目最后。
- 把 demo 当 verification。
- 只记录 pass/fail，不保留原始数据。
- 同一个简单回归反复手工执行。
- 测试配置与正式配置长期漂移。
- 一次整机试验承担太多未知。

这些是本手册根据前述证据做的工程归纳，不应作为“SpaceX 官方反模式列表”引用。

## 11. 医疗器械尤其应该学的部分

医疗器械不能复制“试飞爆炸”的表面形式，但非常应该复制：

- 设计可测试；
- 便宜层级先暴露问题；
- 自动回归；
- 完整数据留存；
- 配置可追踪；
- 越接近患者，门槛越严。

这里是**跨行业迁移建议**，不是对 SpaceX 医疗合规经验的陈述。

换句话说：

> **把失败往患者之前、往更便宜的工程层级推。**
