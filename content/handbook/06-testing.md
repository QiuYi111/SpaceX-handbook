“SpaceX 快，所以它少做验证”是一个错误推论。

公开资料显示的方向几乎相反：**越想快速迭代，越需要高带宽测试系统。**

Muratore 强调设计可测试的系统，并尽可能 Test What You Fly / Test Like You Fly。{{< source "SX-002" >}}

SpaceX 软件团队也公开描述过持续集成、自动测试、硬件在环、人工测试和完整任务模拟；安全关键软件需要更严格的检查。{{< source "SX-006" >}}{{< source "SX-008" >}}

## 1. 测试不是项目尾声

如果产品设计完成后才开始问：

> “这个东西怎么测？”

通常已经太晚。

一个好的工程设计，从早期就在回答：

- 哪些关键状态能观测？
- 故障发生时能不能定位？
- 哪些接口需要 test point？
- 哪些测试可以自动跑？
- 哪些环境必须复现？
- 哪些数据必须记录？

**可测试性本身就是设计属性。**

## 2. Test What You Fly

测试件与飞行件/正式产品之间差异越大，测试结论越弱。

如果测试使用：

- 不同线束；
- 不同软件；
- 不同工装边界；
- 不同材料；
- 不同配置参数；

那么“通过测试”可能并不能证明正式系统。

因此一个重要纪律是：

> **尽量让测试对象、配置和环境接近真实使用状态。**

## 3. 分层测试，而不是只做整机

高质量测试体系通常是一座金字塔：

### 单元 / 零件

便宜、快、适合大量回归。

### 子系统

验证真实接口和局部耦合。

### 硬件在环

让真实硬件与模拟环境闭环。

### 集成系统

发现跨系统耦合问题。

### 真实任务 / 现场

验证只有真实环境才能暴露的问题。

快的团队不是跳过下层测试，而是**让每一层都尽可能自动、高频、低成本**，从而减少把简单错误带到昂贵整机测试。

## 4. 自动化测试是研发吞吐基础设施

如果每次改软件都要人工花两天重新验证，团队会自然减少发布。

如果自动测试能在每次 merge 后运行，发布频率就可以显著增加。

SpaceX 软件公开访谈展示了这种思路：自动测试和 CI 承担大量重复验证，而人工测试和完整任务模拟用于覆盖自动化难以替代的场景。{{< source "SX-008" >}}

对硬件同样成立：

- 自动采集；
- 自动生成 report；
- 自动比较 golden data；
- 自动报警；
- 自动回归。

测试自动化的目标不是“少雇测试工程师”，而是让工程师**敢于更频繁修改系统**。

## 5. 失败后首先保护数据

一个昂贵试验最糟糕的结果不是失败，而是：

> **失败了，却没有足够数据知道为什么。**

因此在试验前就应该检查：

- 关键传感器是否覆盖；
- 采样率是否足够；
- 时钟是否同步；
- 故障前数据是否缓存；
- 视频/遥测是否能保留；
- 触发条件是否可靠。

试验硬件可以损失，信息不能轻易丢。

## 6. 测试强度跟后果一起变化

开发原型和正式载人系统显然不能采用同一门槛。

更合理的结构是：

- **早期探索**：快速关闭未知；
- **设计验证**：证明设计满足要求；
- **qualification**：证明设计余量；
- **生产 acceptance**：证明每件产品符合已验证设计；
- **高后果正式任务**：额外独立检查、故障场景和完整系统验证。

因此 SpaceX 方法并不是统一“更松”，而是把测试资源集中到真正影响风险的地方。

## 7. 测试不是演示

演示的目标：

> 成功给别人看。

测试的目标：

> 尽可能有效地发现系统哪里错。

所以真正有价值的测试应该愿意进入边界：

- 高低温；
- 极限载荷；
- 故障注入；
- 断连；
- 异常输入；
- 最差组合。

如果团队总是选择“最容易通过”的条件，它在做 demo，不是在做 verification。

## 8. 一个简单的测试定义

每个重要测试至少回答：

| 项目 | 问题 |
|---|---|
| Question | 我们到底想知道什么 |
| Configuration | 测的具体版本是什么 |
| Pass criteria | 什么结果算通过 |
| Instrumentation | 需要测哪些量 |
| Failure handling | 失败时如何保证安全和数据 |
| Decision | 结果出来后会改变什么决定 |

如果最后一项回答不了：

> “无论结果如何，我们都不会改任何决定。”

那这个测试很可能没有必要。

## 9. 反模式

- 测试写在项目最后。
- 把 demo 当 verification。
- 只记录 pass/fail，不保留原始数据。
- 同一个简单回归反复手工执行。
- 测试配置与正式配置长期漂移。
- 一次整机试验承担太多未知。

## 10. 医疗器械尤其应该学的部分

医疗器械不能复制“试飞爆炸”的表面形式，但非常应该复制：

- 设计可测试；
- 便宜层级先暴露问题；
- 自动回归；
- 完整数据留存；
- 配置可追踪；
- 越接近患者，门槛越严。

换句话说：

> **把失败往患者之前、往更便宜的工程层级推。**
