# SX-002 · Muratore 2012

## 为什么重要

John Muratore 当时负责 SpaceX 系统工程。这份 2012 年 AIAA CASE 演讲几乎是公开资料里最接近“SpaceX 早期工程操作系统原典”的文件。

当前站内入口改为可访问的逐页全文镜像；历史原件文件名为 `CASE2012_2-4_Muratore_presentation.pdf`，页脚标注 `© Space Exploration Technologies Corp.` 与日期 `9/28/2012`。因此这里把它按 **P0\*** 使用：内容是 SpaceX 当年的一手演讲，但我们现在通过镜像读取，而不是依赖已经失效/不稳定的原 AIAA 链接。

## 精确定位

优先看以下页，不必只引用整份材料：

- **p.7 — Central Philosophy**：systems-oriented culture；Responsibility；设计可测试系统；`test what you fly`；多层级严格测试。
- **p.11 — More Specifics**：系统级任务分散到各部门；公司内 integrator 网络；顶层用户需求跟踪验证；低层参数持续 trade；`TOOLS NOT RULES`；`Test rigorously and often`。
- **p.12 — Traditional Vee / SpaceX**：顶层需求保持，关键设计参数在建模、分析、开发测试中反复调整；单位按预测/实测环境做 qualification。
- **p.13–14 — limited subcontracts / rapid design-build-test**：称当时火箭干质量 >70% 从原材料开始内部制造；并把有限分包与参数 trade 速度联系起来；强调多轮 design-build-test，用经验回灌设计；系统接近 final qualification、first flight、production 后文档和流程更正式。
- **p.15 — Test Like You Fly, Test What You Fly**：列出 Hawthorne ironbird、McGregor engine test、stage firing、发射场 HIL、wet dress、static fire 等集成测试节点。
- **p.16 — Flexible test hierarchy**：区分 development / qualification / acceptance；明确 acceptance 检查 workmanship 与 functionality，并写明 all hardware acceptance tested；HITL 用于硬件-软件集成，并随硬件/软件变更运行。
- **p.17–18 — test examples / test process**：给出 Dragon/Falcon 部件、总成、端到端测试例子，并画出从部件测试到 integrated stage firing、WDR、pad static firing、post-test/flight analysis、Flight Readiness Review 的链路。
- **p.19 — Closing Thoughts**：明确警告过多组织、规则和流程会破坏创造力与性能，同时主张在创造力与系统工程之间取平衡。

## 能证明什么

- SpaceX 把自己描述为 systems-oriented culture，目标是可靠、安全的系统集成。
- 明确提出 Responsibility：没有工程流程能替代具体的人把事情做对。
- 系统级任务被分到各部门，同时再用跨公司的 integrator 网络连接。
- 顶层用户需求要跟踪、验证；其下设计参数在开发阶段持续 trade。
- 使用现代信息工具替代部分传统 control board，强调 Tools not Rules。
- 强调 rigorous and frequent testing；并且给出了具体测试层级、地点和集成节点，而不只是口号。
- 明确采用多轮 design-build-test，用经验回灌设计。
- 随着系统进入 qualification、first flight、production，文档和流程逐渐正式。
- 2012 年材料称火箭超过 70% 干质量在 SpaceX 内部从原材料制造，用来说明有限分包如何缩短参数 trade。

## 不能据此推出

- 这是 **2012 年快照**，不能假定 2026 年 Falcon、Dragon、Starship、Starlink 仍逐项采用完全相同的测试流程。
- 这是公司自己公开的演讲材料，不等于独立审计结果。
- “Tools not Rules” 不是“没有规则”。
- “低层需求可交易”不是允许删除安全、法规或客户顶层义务。
- `>70% dry mass` 是当时 Falcon 系列语境下的公司表述，不能外推成今天所有 SpaceX 产品都保持同一比例。
- p.16 的 development / qualification / acceptance 定义可以证明当时 SpaceX 的测试分层，但不应脱离 2012 语境改写成今日全公司的唯一正式标准。
